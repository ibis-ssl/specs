# Atlas：2基板4ステアのCAN割当

更新日：2026-11-17。**ユーザー確定要求を含む未実装の通信設計**。現行Orion・電源基板の通信契約を変更する文書ではない。
CAN ID・機器間の周期・単位・停止・転送方式の設計上の定義先は本書とする。実装済み契約への移行はMainとステアの適合確認後に行う。
既存契約は[Orion CAN](../common/orion_can.md)、[FW更新](../common/firmware_update.md)を参照する。

## 1. 確定した要求

- DualDCMotorDriver_V4を2基板使用し、各基板はローカル軸M0/M1を制御する。
- Flashに保存する`board_id=0/1`で識別する。全体軸番号は`g = (board_id << 1) | axis`、axis=0/1。
- 角度指令は基板0が0x120/0x121、基板1が0x122/0x123。
- ステア電流は0x230〜0x233。0x234は電源用である。
- ステアの出力指令に使う範囲は0x120〜0x1FF、追加センサーは0x250〜0x2FF、設定・モード変更は0x320〜0x4FF。
- **軸状態・異常用の0x270系は設けず、全ボード共通のエラーID 0x000を使用する。**
- **校正パラメーター要求は設けない。ステアは約1秒周期で、Mainの要求なしに校正パラメーター一式を無条件に送信する。**
- 電源基板はOrionと共通で、電源側のID・payload・タイムアウト・更新契約は変更しない。上記の範囲区分を既存の電源/ドリブラー/キッカーへ遡って適用しない。

4基の物理車輪位置とgの対応、CAN1/CAN2への実配線は未確定。各IDをどちらのバスで使うかはMainと機体配線で確定する。

## 3. 校正パラメーターの約1秒周期送信

Main接続・要求・値の変更を送信条件にせず、board_id確定済みの基板は、非駆動時を含め約1秒ごとに各軸の一組を送信する。
未校正時も送信を省略せず、未校正/無効を明示する。ゼロを有効な端位置・CPR等として偽装しない。
board_id未設定時は送信先IDを確定できないため、通常CANへ送信せずRTTで設定する。

- **一組全体を約1秒ごとに再送する**のであり、1秒に1要素だけ進める方式ではない。
- 要求・購読・ACK・再送要求のプロトコルを追加しない。欠落時は次の周期で再取得する。
- 1周期の先頭でスナップショットを固定し、周期sequence/世代番号、項目数、有効flags、項目番号、終了情報/CRCを含める案。
- Mainは同一周期の一式を検証してから採用し、途中の値を制御へ反映しない。途中から受信した場合は次の完全な周期を待つ。
- 8 byteに収まらないデータは同じ軸IDで複数フレームに分割する。例：`parameter_id:u8 / cycle_seq:u8 / index:u16 / value:u32`。具体的な項目表、型、CRC範囲とcycle_seq周回時の判定は未確定。
- 2基板4軸の送信開始を分散し、低優先IDの送信を1秒内に平準化する。期限を超えた不完全周期を溜めず、次周期の新しい一式へ切り替える。
- CAN異常・FW更新中はハードウェア上送信できない場合がある。欠落検出と更新終了後の周期送信復帰を定義する。送信のために通常運転や校正動作を自動開始しない。

Mainが必要とする項目集合（測定端・中立・CPR・極性・LUT等）は未確定である。LUTを除外することは決定していない。
例えば1軸あたりPフレームの一式なら、4軸・1 Hzで**4Pフレーム/秒**を常時消費する。
256要素LUTを各1フレームにすると、LUTだけで1024フレーム/秒となり、DLC8・135 bit/フレームの概算で1 Mbpsの約13.8%を追加消費する。
必要項目を確定したうえで、型に応じた要素の詰込みを検討する。帯域が足りないことを理由に無断で要求式へ戻したり、一式の周期を伸ばしたりしない。

## 4. 共通エラー0x000と変更しない電源仕様

電源を含む既存ノードは[Orion CAN](../common/orion_can.md)の契約を維持する。
0x000の既存配置はbyte0..1:uint16、byte2..3:uint16、byte4..7:float32、LEである。
Orion文書では前半を「エラーID/補足情報」、旧Atlas CSVでは「エラー検出ノードID/エラータイプ」と呼んでおり、**配置が同じでも値の意味を同一と断定しない**。
電源側FWを変更せず受けられるエラー体系・ステア原因軸の表現・基板共有faultの識別値を、Main/既存電源実装と照合して確定する。

0x000は停止優先で処理する案。受信ごとに再発報してストームを起こさない。エラー解除、再通知周期、同時に複数ノードが送る場合の調停は未確定。
Main生存確認や通常状態の送信には使わない。

特に変更しない電源系の割当は0x001リセット、0x010電源制御、0x110キッカー、0x215/0x216電圧、0x224温度、0x234電流である。
電源制御0x010の保護パラメーターは既存契約の**byte1..4**へfloatを載せる。旧Atlas CSVの見た目からbyte4開始等へ変更しない。
0x010の既存ハートビート/タイムアウト、キック動作、給電条件、電源更新用ノード100も変更しない。ステアの停止方式を電源へ新規要求しない。

## 5. FW更新と既存予約との衝突

既存[更新契約](../common/firmware_update.md)はCANデータ0x480〜0x4FF、command 0x610、reply 0x650+node、version照会0x611を使用する。
したがって、前案のステア独自更新0x480/0x481/0x482と0x490/0x491/0x492は**採用しない**。
ステア校正周期送信は0x600〜0x603のみを候補とし、0x610・0x611や0x650以降を校正の項目ごとに無制限に占有しない。

ステア現行FWの独自更新0x600/0x601/0x602+offsetも校正データと直接衝突する。
同一バスで新しい周期送信と旧更新を併用しない。移行時はステアのアプリ・ブート・更新ホストをまとめて変更する必要がある。
電源更新契約を動かして回避せず、ステアを既存更新へ適合させるか、既存予約と衝突しない独立IDを割り当てるかを確定する。
現在のV4更新形式とOrion更新形式は、データ長・CRC・手順も異なるため、IDの置換だけで互換にはならない。確定までステア更新はST-Linkを使用する。

## 6. 周期・帯域の検討値

角度指令100 Hz/軸、角度帰還100 Hz/軸、電流20 Hz/軸、磁気/AB10 Hz/軸、基板診断1 Hz/基板、温度2 Hz/軸、生存通知20 Hz/基板を初期候補とする。
専用軸状態0x270系の撤回後は、校正を除いて970フレーム/秒、DLC8・135 bit/フレーム換算で約13.1%。
校正一式Pフレーム/軸を加えた概算は`135 × (970 + 4P) / 1,000,000`である。
同一バスでC610の4台×1 kHz状態とMainの1 kHzグループ指令がある例では、さらに約67.5%を消費する。実際のバス分割・DLC・周期と校正データ量を確定し、最悪遅延を測る。
これらは初期検討値であり、現行の周期や遅延保証ではない。

## 7. 保存IDと実装前に確定する事項

board_idはFlashで個体に固定し、未設定をID0として送信しない。停止中にUIDを照合して設定し、再起動でアプリ・ブートへ同じIDを反映する。
同一IDの2台はCAN ACKでは識別できないため、1台ずつの設定と全96 bit UIDの配置確認を行う。
保存形式・Flashレイアウト・V3設定からの移行はステア実装repoの責務とし、旧can_offset=0/16をそのままboard_id=0/1として再解釈しない。

未決の共通契約は次のとおり。

1. 物理車輪位置、バス、角度の単位/正方向/原点/多回転、指令周期・期限。
2. 追加IDの全体予約とpayload。seq付き指令や両軸同周期反映が必要か。2本の連続IDだけでは原子的反映にならない。
3. 正常状態・初期化有効性の載せ方、共通0x000の値体系・解除条件、旧0x310校正指令の利用有無。
4. 校正パラメーター一式の項目・型・有効性・sequence・CRCと、全量を約1秒ごとに送る帯域設計。
5. 電源契約を維持したステア更新の適合方式、通常CANと診断の所有権・モード遷移。

## 8. 実装照合の範囲

2026-11-17に`4WS_MainFW`の`power_packet.c`、`orion_telemetry.c`、`doc/specs_migration.md`を参照した。
Mainの現在のデコーダーは8 byte限定で、0x250系・0x600系校正は未対応。短いDLCとNaNの扱いも現実装へ適合させる必要がある。
旧Atlas CSVと本書の配置が違う場合、電源の既存契約を優先し、相手実装を未確認の推測で変更しない。
Main・ステア・電源の結合確認済みを意味しない。実装上の差・検証結果は各実装repoで管理する。
